PART 1: PROJECT SUMMARY (SIMPLE + TECH/NON-TECH VIEW)
====================================================================

1.1 What EN-VISION is
EN-VISION is an AI-assisted energy intelligence platform designed to monitor, analyze, and improve energy usage in industrial and enterprise environments.

In simple language:
- It reads energy data from devices, meters, departments, and locations.
- It turns raw numbers into insights like "where power is being wasted" and "what should be optimized first".
- It predicts upcoming consumption, detects unusual behavior, and estimates costs and carbon impact.
- It helps operations teams make practical decisions with dashboards, alerts, recommendations, and trend analysis.

1.2 Problem EN-VISION solves
Most organizations have:
- fragmented energy data,
- delayed reporting,
- no anomaly visibility,
- no predictive planning,
- unclear cost and carbon accountability.

EN-VISION addresses this by:
- centralizing data,
- adding real-time style analytics,
- surfacing anomalies and root causes,
- forecasting future demand,
- giving KPI-level executive visibility.

1.3 Goals of the project
Primary goals:
- Build a usable, scalable platform for energy optimization.
- Reduce avoidable energy and cost inefficiencies.
- Detect abnormal consumption early.
- Improve planning using forecast data.
- Track sustainability indicators (emissions/carbon).
- Provide role-based access and secure usage.

Academic and process goals:
- Demonstrate iterative Agile delivery through sprint cycles.
- Maintain backlog refinement, sprint commitment, and retrospective quality.
- Produce sprint-level artifacts (functional docs, architecture updates, test documents, demos).

1.4 Who benefits
Operational teams:
- Faster identification of high-consumption zones and devices.
- Actionable recommendations for saving energy.

Management:
- Better decision making using KPIs and trend summaries.
- Clear cost and carbon visibility for governance and reporting.

Sustainability teams:
- Better emissions insight and source-level understanding.

Developers and analysts:
- Clean API and modular architecture for extension.

1.5 Business and non-technical impact
Business value:
- Lower unnecessary energy spend.
- Better planning of peak load periods.
- Reduced risk from hidden anomalies.
- Improved transparency across departments.

Non-technical value:
- Better cross-team communication with a unified dashboard.
- Better reporting discipline via sprint process and documentation.
- Better confidence in data-backed operational decisions.

1.6 Current solution maturity snapshot
Current maturity highlights:
- Dashboard with multiple analytical tabs is implemented.
- Anomaly intelligence has source attribution and dual anomaly metrics.
- Cost modeling aligned to INR and India average tariff (Rs 8.2 per kWh).

PART 2: PROPER PROJECT EXPLANATION (FOR A DEV/COMPANION)
====================================================================

2.1 High-level architecture
Frontend:
- Next.js App Router + React + TypeScript
- Framer Motion for transitions and activation experience
- Recharts for visual analytics
- TanStack Query + Axios for data fetching/caching

Backend:
- FastAPI + SQLAlchemy ORM
- Domain-focused service routers and service modules
- JWT + bcrypt based authentication/authorization
- PostgreSQL-style data model assumptions via SQLAlchemy entities

2.2 Module-level backend organization
Backend folders (major):
- services/dashboard/*: KPI, trend, anomaly, cost, carbon, forecast, filters, AI insights, location consumption
- services/ingestion/*: CSV/data ingestion pipeline
- services/auth/*: security, dependencies, login/profile/password APIs
- models/*: ORM entities (company, department, device, meter, energy, carbon, user, etc.)
- schemas/*: response/request contracts
- utils/*: shared helpers (date range, tariff)

2.3 Frontend organization
Frontend folders (major):
- app/*: routing, page composition, login, profile, change-password
- components/dashboard/*: sidebar, header, cards, controls
- components/tabs/*: home, energy, anomalies, forecasting, carbon, power-bi
- hooks/*: data hooks and UI helper hooks
- lib/api/*: API client + typed dashboard API layer
- components/auth/*: auth provider, protected route, activation component
- types/*: dashboard and auth types

2.4 Data and workflow integration
End-to-end request flow:
1. User logs in from /login using username/password.
2. Backend /auth/login validates bcrypt password and returns JWT token.
3. Token is stored in browser storage/cookie, auth context is hydrated.
4. Protected routes require token presence and valid user session.
5. Axios client adds Bearer token automatically to dashboard requests.
6. Backend dashboard router checks current user dependency before serving data.
7. Frontend tabs fetch data via hooks and display KPI/charts/cards.

2.5 Authentication and authorization (implemented)
Implemented auth features:
- Login endpoint: /auth/login
- Current user endpoint: /auth/me
- Logout endpoint: /auth/logout
- Profile update endpoint: /auth/profile (PATCH)
- Change password endpoint: /auth/change-password (POST)

Role logic:
- Admin: full tab access including Power BI section.
- User: broad analytics access excluding highest-level restricted view.
- Viewer: read-only narrowed dashboard set (home, energy, anomalies).

UI role behavior:
- Sidebar dynamically filters visible tabs based on role.
- Active tab auto-corrects if role cannot access selected tab.
- Header profile area shows user and role.

2.6 Anomaly system evolution and current behavior
Anomaly improvements delivered:
- Fixed anomaly zero-result bug caused by query/grouping behavior.
- Added proper threshold propagation.
- Shifted anomaly scoring to residual logic (actual - baseline z-score).
- Added source attribution fields:
  - source_device
  - source_zone
  - source_department
  plus IDs for reliable filter actions.
- Added click-to-filter controls from anomaly rows.
- Added severity distribution chart in anomaly tab.
- Added two key metrics:
  - Net anomalies (scope-aware)
  - Any-device anomaly days

Why dual metrics matter:
- Aggregate-level anomalies and device-level anomaly days answer different operational questions.
- This removes confusion when department-level counts differ from per-device observations.

2.7 Cost, currency, and realism updates
Cost logic was standardized to:
- cost = total_kwh * 8.2 INR

Key updates:
- Introduced central tariff utility (utils/tariff.py).
- Switched key backend services from stored/legacy cost dependence to consistent derived INR cost.
- Updated frontend cost display from GBP to INR in major active analytics components.
- Added tariff transparency labels where relevant.
